STAGE 2: SPRINT 2 — FINANCIAL LOGIC & AI DISPATCH ENGINE (สมองกลประเมินคุ้มทุน)
--------------------------------------------------------------------------------
เป้าหมาย: นำสูตรธุรกิจใส่ในระบบ แปลงหน่วยไฟเป็นเงินบาท และวิเคราะห์ Cost of Inaction 30 วัน

[PROMPT]
ยอดเยี่ยมมาก! ตอนนี้เราจะเพิ่ม "หัวใจทางธุรกิจ" (Business & Financial Logic) ใน Sprint 2
ให้สร้างโมดูล financial.py เพื่อคำนวณตัวเลขและประเมินจุดคุ้มทุนการล้างแผงตามสูตรดังนี้:

1. สูตร Expected Yield (กำลังผลิตที่ควรได้ตามทฤษฎีเมื่อแดดส่อง):
   expected_kw = capacity_kwp * (irradiance_w_m2 / 1000.0) * 0.95

2. สูตร Soiling Loss % (อัตราการสูญเสียจากฝุ่น):
   soiling_loss_pct = max(0.0, ((expected_kw - pv_power_kw) / expected_kw) * 100.0)

3. สถานะความสะอาดแผงโซลาร์ (Soiling Status):
   - Soiling Loss < 5.0%: 🟢 ปกติ (แผงสะอาด)
   - Soiling Loss 5.0% - 15.0%: 🟡 เฝ้าระวัง (ฝุ่นปานกลาง)
   - Soiling Loss >= 15.0%: 🔴 วิกฤต (ฝุ่นหนาแน่นสูง)

4. สูตรคำนวณเงินบาทที่สูญเสียต่อวัน (Daily Revenue Lost THB):
   - daily_lost_kwh = capacity_kwp * 4.5 * 0.95 * (soiling_loss_pct / 100.0)
   - daily_lost_thb = daily_lost_kwh * 2.20 (อิง Feed-in tariff 2.20 บ./kWh)

5. สูตร AI Dispatch Recommendation (วิเคราะห์จุดคุ้มทุน Cost of Inaction 30 วัน):
   - projected_30d_loss = daily_lost_thb * 30 วัน
   - cleaning_cost = 15,000 บาท (ค่าบริการล้างแผงต่อไซต์)
   - เงื่อนไขตัดสินใจ:
     * หาก projected_30d_loss > cleaning_cost:
       ผลประโยชน์สุทธิ (Net Saving) = projected_30d_loss - cleaning_cost
       แนะนำ: "⚠️ ต้องดำเนินการ: สั่งล้างทันทีคุ้มค่ากว่า (ประหยัดสุทธิ +X บาท)" -> ป้ายสีแดง
     * หาก projected_30d_loss <= cleaning_cost:
       แนะนำ: "ℹ️ เฝ้าระวัง: ยังไม่จำเป็นต้องล้างวันนี้" -> ป้ายสีเขียว

*** ข้อกำหนดสำคัญที่สุด (Night-time Fallback Rule) ***:
หาก irradiance_w_m2 < 150.0 W/m² (ช่วงกลางคืนหรือเช้ามืดที่ไม่มีแดด) ห้ามคำนวณ Expected Yield จากแดดสดเด็ดขาด เพราะจะทำให้หารด้วย 0 หรือได้ค่าติดลบ!
ให้ทำ fallback โดยไปดึงค่า loss % และ daily_lost_thb จากข้อมูลของเมื่อวาน (GET /api/v1/{GROUP_ID}/history/last/1/{site_id}) แทน

อัปเดต app.py และหน้าเว็บ Dashboard ให้แสดง:
- Badge สีสถานะ 🟢/🟡/🔴 บนการ์ดแต่ละไซต์
- ตัวเลขเงินที่สูญเสีย (บาท/วัน)
- กล่องคำแนะนำ AI Decision Box ชัดเจนว่าไซต์ไหนต้องสั่งล้างด่วน

STAGE 4: TROUBLESHOOTING & EMERGENCY FIXES (เมื่อเจอปัญหาหน้างาน)
--------------------------------------------------------------------------------

กรณีที่ 1: หน้าเว็บโหลดช้า หรือเจอข้อผิดพลาด 504 Gateway Timeout จาก Render
[PROMPT]
เนื่องจาก API ภายนอกบน Render อาจใช้เวลาตอบสนองนานเมื่อถูกเรียกพร้อมกันบ่อยๆ 
ช่วยเพิ่มระบบ Caching ใน Backend ของเรา:
1. เก็บผลลัพธ์ของ sites, telemetry และ history ไว้ในหน่วยความจำ (In-memory Cache) หรือ SQLite ชั่วคราว
2. ทำ Background Sync ทำงานเบื้องหลังทุกๆ 60 วินาที เพื่อคอยอัปเดตข้อมูลจาก Solar API
3. เมื่อหน้าเว็บเรียก GET /api/snapshot ให้ส่งข้อมูลจาก Local Cache ออกไปทันที โดยผู้ใช้ไม่ต้องรอ Request ภายนอก ทำให้หน้าเว็บโหลดเร็วขึ้นและไม่ติด 504 Timeout
[/PROMPT]

กรณีที่ 2: รันแล้วเจอปัญหา Port 8000 ชนกัน (Address already in use)
[PROMPT]
พอร์ต 8000 กำลังถูกใช้งานค้างอยู่ ช่วยเขียนคำสั่ง shell สำหรับค้นหาและ kill process ที่ค้างบน Port 8000 ให้เด็ดขาดก่อนเริ่มรัน uvicorn ใหม่อีกครั้ง
(คำสั่งที่แนะนำ: kill -9 $(lsof -t -i:8000) 2>/dev/null || true)
[/PROMPT]

กรณีที่ 3: สไตล์ Tailwind CSS หรือปุ่มกดคลิกแล้วไม่ทำงาน
[PROMPT]
ตรวจสอบหน้า index.html:
1. ตรวจสอบว่าโหลด Tailwind CDN และ Chart.js CDN ครบถ้วนหรือไม่
2. ตรวจสอบคำสั่ง fetch() ใน JavaScript ทั้งหมดว่าใช้ Relative Path เช่น fetch('./api/snapshot') หรือไม่ ห้ามมี '/' นำหน้า
3. ตรวจสอบ Console Log ใน Browser Developer Tools ให้มั่นใจว่าไม่มี TypeError หรือ Unhandled Promise Rejection
